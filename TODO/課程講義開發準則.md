Last updated: 2026-05-13

用途：後續開發本 Cocos Creator 專案時，優先遵守這份準則，降低 merge 衝突、場景壞掉、手感不穩與效能問題。

## 1. 專案協作與 Git 原則

### 必須使用 Git

- 每次完成一個可描述的小功能後就應該提交。
- 不要等大量 scene / prefab / asset 變動累積後才提交，否則很難 rollback。
- 遇到 Cocos 崩潰、scene 異常、metadata 壞掉時，先用 Git 檢查哪些檔案被意外改動。

### 避免多人同時修改同一個 scene

Cocos 的 `.fire` scene、`.prefab`、`.meta` 都是 engine 產生的 serialized data。它們雖然看起來像 JSON，但很容易產生難解的 merge conflict。

開發時應避免：

- 多人同時編輯 `MiniGame2.fire`
- 多人同時移動同一批 node
- 多人同時調同一個 prefab 的 Inspector 欄位

比較好的做法：

- 每個人負責不同 scene 或不同 prefab。
- 真正要整合時，由一個人負責打開主 scene，把別人的 prefab / scene 內容透過 Cocos Editor 整合進來。
- 對大型功能，優先做成 prefab，再由 manager script 在 scene load 時 instantiate。

## 2. Asset 與 `.meta` 管理

### Asset 要透過 Cocos Editor 匯入

課程強調：圖片、音效等 asset 匯入時，Cocos 會產生 `.meta` 與 uuid。若兩個人各自在本機產生不同 uuid，scene 裡的引用就會壞掉。

因此：

- 新圖片、音效、素材應透過 Cocos Editor 匯入或 refresh 後連同 `.meta` 一起提交。
- 不要只複製 `.png`、`.wav` 而忘記 `.meta`。
- 若修改 sprite import setting，如 `Filter Mode: Point`、`Trim Type: None`，要確認 `.meta` 也有被更新。

### Pixel art import 建議

本專案角色與 tiles 多為 pixel art，建議：

```text
Filter Mode: Point
Wrap Mode: Clamp
Gen Mipmaps: false
Trim Type: None
```

若圖片是背景大圖、雲層、漸層，則可以視覺效果決定是否保留 bilinear。

## 3. Scene / Prefab 架構

### Prefab 優先

講義建議將 scene 拆成獨立 prefab，以減少 merge 衝突並提高平行開發能力。

本專案建議拆分：

- `Player` prefab：角色 Sprite、BoxCollider、controller、animator。
- `SolidTile` prefab：tile Sprite + BoxCollider。
- `Hazard` prefab：spikes / lava / saw 等傷害物。
- `Switch` prefab：按鈕或開關。
- `Door` prefab：合作門。
- `GoalZone` prefab：通關區。
- `MovingPlatform` prefab：移動平台。
- `LevelChunk` prefab：一小段平台關卡。

### Scene 只做組裝

`MiniGame2.fire` 應盡量只負責：

- 放置 prefab
- 設定關卡 layout
- 設定 camera / scene manager
- 設定少量場景專屬參數

不要把大量邏輯塞在 scene node 上，否則之後很難重用與 merge。

## 4. Abstraction 與 Dependency 原則

講義提醒：不要讓一個模組直接知道另一個 prefab 的內部 node 路徑，否則改 node 名稱或 hierarchy 就會壞。

避免：

```js
cc.find('Canvas/UI/HP/Text')
```

建議：

- 在 prefab root 放 manager component。
- 對外提供清楚的方法與 property。
- 由 scene manager 或 game manager 在 onLoad 時注入 dependency。

例：

```js
actors.getComponent('ActorManager').injectDependencies(
    ui.getComponent('UIManager')
);
```

套用到本專案：

- Player 不應直接找 UI 內部 node。
- MiniGame clear 時應呼叫 `MiniGameManager.clear(miniGameId)`，而不是直接改 Inventory 內部結構。
- CameraFollow 應只知道 target node，不應知道角色 prefab 內部 Sprite 節點名稱。

## 5. Platformer 物理策略

### 本專案優先使用 kinematic physics

講義指出：

- Dynamic physics 容易設定，但平台跳躍手感較難精準控制。
- Kinematic physics 較難寫，但適合需要好手感的平台遊戲。

本專案目前角色已經是 kinematic：

- 自己控制 `node.x`
- 自己控制 `velocityY`
- 自己做 gravity
- 自己修正 collision

後續應維持這個方向，不要突然混用 `RigidBody` 力量推動玩家，除非整個 controller 重寫。

### Collider 是偵測，不是自動阻擋

Cocos 2D `BoxCollider` 只提供碰撞 callback。若角色是自己改 `node.x/y`，就必須自己寫位置修正。

本專案目前規則：

- Player：BoxCollider + `PinkMonsterController`
- Solid tile：BoxCollider
- Controller：在 `onCollisionEnter / onCollisionStay` 中修正位置

### Ramp 處理

普通斜坡不適合使用 `BoxCollider`，會變成隱形方塊角落，導致上坡卡頓。

短期做法：

- Ramp 只當裝飾，不加 collider。
- 或用 `PolygonCollider` 做三角形碰撞。

長期做法：

- 寫 `RampCollider` / slope height detection。
- 根據角色腳底 x 位置計算斜坡 y 高度。
- 腳底低於斜坡線時，把角色貼到斜坡上。

## 6. 跳躍手感技巧

### Coyote Time

講義介紹 Coyote Time：玩家剛離開平台的短時間內仍允許跳躍，用來增加容錯。

本專案可採用：

```text
coyoteTime: 0.08 ~ 0.15 秒
jumpBuffer: 0.08 ~ 0.15 秒
```

目前已有類似 `groundContactGrace` 的概念，但要小心：

- 太短：站在 block 上 grounded 會抖。
- 太長：離開平台後會漂在空中。

之後可整理成更清楚的：

- `grounded`
- `lastGroundedTime`
- `lastJumpPressedTime`
- `canJump()`

### Double Jump

Double jump 可增加容錯，也能取代部分 coyote time 的需求。

本專案目前：

- `maxJumpCount = 2`
- 第二跳時生成 `Double_Jump_Dust_5`

注意：

- 長按跳躍不應連續觸發 double jump。
- 必須用 `jumpPressed` 避免 keyboard repeat。
- 落地時才 reset `jumpCount`。

## 7. Camera 設計

講義列出常見 camera 技巧：

- offset
- interpolation / smoothing
- follow target
- soft zone / dead zone
- bounds
- camera collision
- shake
- zoom

本專案目前採用：

- `CameraFollow`
- follow target：Player
- offset：`(0, 80)`
- followY：目前可關閉或依關卡需求開啟
- bounds：避免露出地圖外黑邊

### Camera bounds 注意事項

Camera 的座標通常代表畫面中心，不是畫面左邊。

若畫面寬是 `960`，地圖左邊界是 `leftEdgeX`，camera 最小中心 x 應約為：

```text
leftEdgeX + 480
```

若 Canvas 或 Player parent 有偏移，必須注意 local / world coordinate 差異。

實務建議：

- 先用明確 `minX` 調到不露黑邊。
- 再決定是否使用自動計算。
- 避免每次 Refresh 後忘記打開 `Use Bounds`。

## 8. Tile / Level 建置方式

### 初期可直接用已切好的 png tile 排場景

目前素材已經在：

```text
assets/tiles/Default
```

初期快速灰盒可以直接拖 tile 到 scene，但要整理 hierarchy：

```text
Canvas
  Level
    Ground
    Platforms
    Decorations
    Hazards
```

不要把所有 tile 散放在 Canvas 根目錄。

### Solid tile 建議做成 prefab

每個可站立 tile 都應有：

```text
Sprite
BoxCollider
```

建議做一個 `SolidTile` prefab，之後複製 prefab 來排地圖，避免手動漏加 collider。

## 9. 視覺與場景技巧

### Parallax Scrolling

背景可分多層，遠處移動較慢、近處移動較快。遠景可以更淡，營造深度。

本專案已有 cloud / background layer，可沿用：

- 遠景：低速度、淡色
- 近景：較快速度
- 前景裝飾：可略快或固定

### Transition

場景切換不一定只用 fade。可用：

- 黑色遮罩移動
- portal / black hole 圖片遮住畫面
- 粒子或 dust 快速遮擋 camera

本專案主題是外星人、黑洞、異常維度，適合用 portal / black-hole transition。

### Fake lighting / fake water

2D lighting 和 water 不必先做真實物理。可用：

- 半透明黑色 overlay 做聚光燈
- 不同 alpha mask 做光照形狀
- 水下區域用藍綠 overlay
- 入水 / 出水時生成 ripple particle

## 10. AI 與敵人

課程建議初期用 rule-based AI。

適合本專案：

- 敵人巡邏：往前走，快掉下平台時轉向。
- 視線攻擊：玩家在同高度或距離內才發射子彈。
- Boss / monster：依 HP 區間改變攻擊機率。

避免一開始做太複雜的 pathfinding。若未來需要追玩家：

- tile/grid 地圖可用 A*
- 非 grid 地圖才考慮 navmesh

## 11. Procedural Generation

本專案 demo 不應優先做 procedural generation。

若未來需要：

- Endless runner：用一組 prefab pattern 隨機接在後面。
- Dungeon：用房間 prefab + 連接規則。
- Terrain：midpoint displacement 可生成地形輪廓，再轉成 tile/collider。

目前階段應優先手工製作穩定關卡。

## 12. Multiplayer

講義區分 local multiplayer 與 online multiplayer。

本專案建議：

- Demo baseline：local two-player。
- Online / invite code：bonus，不要阻塞 demo。

Local two-player 做法：

- Player 1：WASD 或 A/D/W
- Player 2：另一組按鍵，例如 J/L/I 或方向鍵
- Camera 可追兩個玩家平均位置或 bounding box

Mini Game 2 合作關卡應確保：

- 一個人不能單獨通關。
- 雙人到達 goal 才 clear。
- 失敗或掉落能 respawn，不會 softlock。

## 13. Node Pooling

講義提醒頻繁 create/destroy node 會造成效能成本。

本專案目前可先不用過度優化，但以下物件適合未來改用 `cc.NodePool`：

- bullets
- enemies
- particles
- dust effects
- coins / pickups
- hit effects

基本策略：

```text
onLoad 建立 NodePool
需要時 get()
用完 put()
不要一直 new cc.Node / destroy()
```

目前 `Double_Jump_Dust` 是動態建立，若之後大量使用，可改成 pooling。

## 14. 後續 Codex 開發守則

後續請優先遵守：

1. 不隨便大改 `.fire`，除非任務明確需要。
2. 新功能優先做成小 script 或 prefab。
3. 碰撞與平台手感維持 kinematic controller，不混用 dynamic rigidbody。
4. 改 scene serialized data 後要檢查 JSON。
5. 改 JS 後要跑語法檢查。
6. Cocos Refresh 後 Inspector 欄位可能被還原，重要設定要重新確認。
7. Pixel art asset 優先 `Filter Mode: Point`。
8. Camera bounds 要用畫面中心概念調整，不要把 player minX 直接當 camera minX。
9. Online multiplayer 不作為 demo 必備條件。
10. 若同一功能需要多人開發，先拆 prefab / manager / interface，再整合。

## 15. 本專案近期建議順序

1. 穩定 Player movement / collision / camera bounds。
2. 把 solid tile 做成 prefab，避免每塊 tile 手動加 collider。
3. 整理 `MiniGame2` scene hierarchy：`Level/Ground/Platforms/Hazards/Goals`。
4. 做 respawn / checkpoint。
5. 做兩人控制版本。
6. 做合作機關：button、door、moving platform。
7. 做 goal zones：兩人都到才 clear。
8. 再加 UI、音效、特效與美術 polish。
